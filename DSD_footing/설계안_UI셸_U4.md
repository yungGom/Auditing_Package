## 0. 진단 결과 (지시대로 구현 전 조사) ★핵심 발견 1건 포함

### 0-1. `box` / `anchor_bbox`의 좌표계·단위 — 실측
```
document.coordinate_space = "pdfplumber-topleft"
box         = {x0: 441.325, top: 466.0, x1: 545.0, bottom: 483.0}
bbox        = [441.325, 466.0, 103.675, 17.0]      # [x, y, w, h]
anchor_bbox = [441.325, 466.0, 103.675, 17.0]      # bbox와 항상 동일
```
- **단위: PDF 포인트. 원점: 지면 좌상단, y는 아래로 증가.**
- 18건 전수 확인: `bbox`는 `box`에서 유도된 값과 정확히 일치하고 `anchor_bbox ===
  bbox`다(불일치 0건). → **셋 중 무엇을 써도 같은 사각형**이며, `anchor_bbox`가
  링 대상이라는 스펙과 `box`가 히트 대상이라는 게 실질적으로 동일 사각형이다.
- 값에 소수가 있다(`441.325`, `545.0028571428571`). `box4()` 주석의 경고대로
  **어느 단계에서도 반올림하지 않는다.**
- 5개 샘플 전부 mediabox `[0, 0, 595, 842]`, `/Rotate` 0, 페이지별 편차 없음
  → pdfplumber ↔ PDF 사용자공간 변환은 `pdfY = pageHeight - top` 단순 뒤집기.

### 0-2. pdf.js 변환 API — vendoring된 v6.2.108에 존재 확인
`build/pdf.mjs`의 `PageViewport` 클래스(907·912행):
```js
convertToViewportPoint(x, y)  // PDF 사용자공간 → 뷰포트(캔버스 CSS px, 좌상단 원점)
convertToPdfPoint(x, y)       // 그 역변환
```
둘 다 `this.transform`(scale·rotation·offset이 이미 합성된 6원소 행렬)을
적용/역적용한다. **확대율과 회전을 우리가 직접 계산할 필요가 없다** — viewport
객체에 이미 들어 있다.

### 0-3. 히트박스 겹침 — 5개 샘플 전수 조사

| 축 | marks | 원본 box 겹침 | 글리프까지 합친 경우 |
|---|---|---|---|
| 삼성전자 | 20 | **1쌍** | 12쌍 |
| LG에너지솔루션 | 16 | 0쌍 | 2쌍 |
| 조선내화(연차) | 30 | **1쌍** | 17쌍 |
| 휴맥스홀딩스 | 50 | **2쌍** | 18쌍 |
| **조선내화(반기) — 게이트 샘플** | 18 | **0쌍** | 5쌍 |

**원본 겹침 4쌍은 전부 같은 패턴이다: A1(세로합)과 A2(가로합)가 표 모서리 셀
(합계행 × 합계열)에서 `box`가 완전히 동일**하다.
```
[삼성 p119]   A2:p119:t2:r6:cx0  box=(515.035, 369.0, 545.003, 383.0)
              A1:p119:t2:r6:c15  box=(515.035, 369.0, 545.003, 383.0)   ← 동일
```
같은 숫자에 대한 서로 다른 두 검증이라 겹치는 게 정상이며, **후보 목록이 필요한
진짜 사례**다.

> ⚠ **게이트 4를 조선내화 반기로는 잴 수 없다**(그 샘플엔 0쌍). 대신 **삼성 p119 /
> 휴맥스 p89·p167 / 조선내화 연차 p75에서 실데이터로 잴 수 있다** — U-3의
> `table_label`처럼 합성에 의존하지 않아도 된다. 게이트 4만 다른 축에서 재는 것을
> 승인 요청드린다.

### 0-4. ★핵심 발견 — 보이는 마크(✗)는 `box` 밖에 그려진다

오버레이 PDF의 **콘텐츠 스트림에서 직접 측정**했다(코드만 읽고 추정하지 않음).
조선내화 반기 p8, `cross:A5:p8:t1:r12:c2`:
```
box    : x0=239.86  x1=316.260   top=330.0  bottom=345.0
글리프 : x  314.760 ~ 321.260    y_top  336.500 ~ 343.000     (콘텐츠 스트림 실측)
```
`render.py`의 `cross(c, x1-1.5, H-b0+2.0, s=6.5)` 공식과 정확히 일치한다.

→ **✗ 글리프 6.5pt 중 5.0pt(77%)가 `box` 오른쪽 바깥에 있다.**
   세로로는 셀 안이지만, 가로로는 대부분 셀 경계를 넘어간다.

**결과: `box`만 히트영역으로 쓰면, 회계사가 눈에 보이는 빨간 ✗를 클릭했을 때
대부분 빗나간다.** 게이트 1(“box 중심점을 클릭”)은 이 문제를 못 잡는다 — 중심은
당연히 box 안이니까.

그렇다고 `box ∪ 글리프`를 평평하게 합치면 겹침이 4쌍 → **54쌍**으로 폭증한다
(위 표 오른쪽 열). 인접 열 마크의 글리프가 옆 칸 `box`를 침범하기 때문이고,
그러면 후보 목록이 상시로 뜬다. 두 방식 다 못 쓴다 → §2의 2단 우선순위로 푼다.

## 1. 좌표 변환 경로 — 단계별 명시 (지시 사항)

**단 하나의 변환 함수만 둔다.** 링 그리기와 히트 판정이 같은 함수를 쓰므로,
링이 눈에 맞게 그려졌다면 히트영역도 반드시 같은 자리다 — 둘이 어긋날 구조적
여지를 없앤다.

```
pdfplumber 사각형 (box: x0, top, x1, bottom)   ← marks.json, PDF pt, 좌상단 원점
  │  y축 뒤집기:  pdfY = pageHeight - y        (pageHeight = viewBox[3] - viewBox[1])
  ▼
PDF 사용자공간 (x, y)                           좌하단 원점
  │  viewport.convertToViewportPoint(x, y)     scale·rotation·offset 합성 적용
  ▼
뷰포트 좌표 (CSS px, 좌상단 원점)                 캔버스 style.width/height와 같은 공간
  │  + canvas.getBoundingClientRect().left/top
  │  × (rect.width / viewport.width)           ← CSS 스케일 방어(보통 1.0)
  ▼
브라우저 client 좌표
```
클릭은 이 경로의 **역방향**이다:
```
click(clientX, clientY)
  → rect 빼기 + (viewport.width / rect.width) 곱하기   → 뷰포트 좌표
  → 마크의 히트 사각형(위 순변환 결과)과 뷰포트 공간에서 직접 비교
```
- **DPR은 이 경로에 등장하지 않는다.** `canvas.style.width = viewport.width + "px"`로
  두었기 때문에 CSS 픽셀 = 뷰포트 좌표이고, DPR은 캔버스 백킹스토어 해상도에만
  쓰인다(U-1 구현 그대로). 그래도 `rect.width / viewport.width` 보정을 넣어
  창 크기·CSS 스케일이 개입해도 안전하게 한다.
- **회전은 직접 다루지 않는다** — `convertToViewportPoint`가 이미 처리한다
  (샘플은 전부 `/Rotate 0`이지만 API에 맡기는 편이 안전).
- **어느 단계에서도 반올림·절삭하지 않는다.** 부동소수로 끝까지 간다.
  비교 시점에만 tolerance를 적용한다(§2).

## 2. 히트 판정 — 2단 우선순위 (§0-4의 딜레마 해법)

```
tier 1 (글리프)  : 실제로 그려진 ✗ / ? 글리프를 중심으로 한 12×12 pt 정사각형
tier 2 (셀 box)  : anchor_bbox 그대로 (= box = bbox)

판정:
  1. tier 1 에 들어오는 마크를 모은다 → 1건이면 선택, 2건 이상이면 후보 목록
  2. 없으면 tier 2 에 들어오는 마크를 모은다 → 1건이면 선택, 2건 이상이면 후보 목록
  3. 없으면 아무것도 선택하지 않는다 (선택 해제)
```

**왜 2단인가**: 평평하게 합치면 54쌍이 겹치지만, 우선순위를 두면 “옆 칸 글리프가
내 셀을 침범” 상황이 애초에 경쟁이 되지 않는다. 글리프를 클릭하면 글리프가 이기고,
숫자를 클릭하면 셀이 이긴다.

**tier 1 크기 검증 (실측)**: 12×12 pt로 잡으면 글리프끼리 충돌은 **정확히 그 4쌍
(A1×A2, 중심거리 0.00pt — 물리적으로 같은 자리)뿐**이고, 그다음으로 가까운 쌍은
**14.00pt** 떨어져 있다. 즉 12는 스펙이 요구한 최소치인 동시에 **사실상 최대치**다
(표 행 피치가 14pt라 14×14로 키우면 위아래 행이 붙는다). 이 수치는 우연이 아니라
경계선 위에 있으니, 나중에 키우고 싶어지면 반드시 다시 재야 한다.

**tolerance**: 비교는 `x0 - EPS <= px <= x1 + EPS` (EPS = 0.01pt). 부동소수 왕복
오차만 흡수하는 값이고, 히트영역을 넓히는 용도가 아니다(넓히는 건 tier 1의 12×12가
담당).

**글리프 중심 좌표**는 `render.py`의 그리기 공식에서 유도한다(§0-4에서 콘텐츠
스트림과 일치 확인):
| kind | 글리프 중심 (pdfplumber 기준) |
|---|---|
| `cross` (A계열) | `(x1 - 1.5 + 3.25, bottom - 5.25)` |
| `cross` (check="C") | `(x1 + 2.0 + 2.5, bottom - 4.0)` |
| `question` | `(x1 - 1.5 + 2.1, bottom - 4.7)` |

> ⚠ 이 표는 `render.py`의 드로잉 공식을 UI가 **복제**한 것이다. 렌더 공식이 바뀌면
> 여기도 같이 바뀌어야 하는데 게이트가 잡아주지 않는다. `ui/web/hit.js` 상단에
> “render.py draw_mark()와 동기화 필요” 주석을 달고, CLAUDE.md 결정에도 남긴다.
> (근본 해법은 `marks.py`가 글리프 사각형까지 내보내는 것인데, 그건 marks.json
> 스키마 변경이라 U-4 범위 밖 — 후속 과제로 등재만 한다.)

## 3. 링 그리기

- 캔버스에 그리지 않는다. 캔버스 위에 **절대배치 오버레이 `<div id="markOverlay">`**
  를 두고 그 안에 링 `<div class="ring">` 하나를 놓는다.
  - 캔버스를 다시 렌더해도 링이 지워지지 않는다(페이지 이동·확대 시 위치만 갱신).
  - `pointer-events: none`으로 두어 클릭은 캔버스로 통과시킨다.
- 위치·크기는 §1 순변환 결과 그대로(`anchor_bbox` 기준). 테두리 `1.5px solid var(--red)`.
- 선택 마크가 현재 페이지가 아니면 링을 숨긴다.
- 확대율 변경 시 `renderPage()`가 새 viewport로 다시 계산 → 링도 같이 갱신.

## 4. 후보 목록 (겹칠 때)

클릭 지점 근처에 작은 팝업. 각 줄에 `account` + 검증 종류(`formula`의 앞부분,
예: “세로 합계” / “가로 합계”). 클릭하면 그 마크를 선택하고 팝업을 닫는다.
바깥 클릭·ESC로 닫힌다. 색은 기존 3색 안에서 해결한다(새 색 없음).

## 5. 버스 계약 — 선택 상태의 소유자를 하나로

U-3에서 `jumpToPage`(sidebar→viewer) / `pageChanged`(viewer→sidebar)를 썼다.
U-4는 양방향이 되므로 **선택 상태의 단일 소유자를 sidebar.js로 못박는다.**

| 이벤트 | 방향 | 뜻 |
|---|---|---|
| `selectMark` | viewer → sidebar | “이 마크를 선택해 달라”(요청). 지면 클릭이 낸다 |
| `selectionChanged` | sidebar → viewer | “선택이 이렇게 됐다”(확정 상태). 페이지 이동 + 링 갱신의 근거 |
| `pageChanged` | viewer → sidebar | U-3 그대로 |

`jumpToPage`는 `selectionChanged`로 흡수한다(마크·페이지·anchor_bbox를 함께 실어
보내므로 별도 이벤트가 필요 없다). **루프가 생기지 않는다**: viewer는
`selectionChanged`를 받아 처리만 하고 되쏘지 않는다.

## 6. 게이트 계획

| 게이트 | 방법 | 자동/수동 |
|---|---|---|
| 1. 18건 전수 클릭 | 각 마크의 `box` 중심을 §1 순변환 → 그 client 좌표를 `page.mouse.click()` → 선택된 id 대조. 실패 0건 요구 | 자동 |
| 2. 75% / 100% / 150% 전배율 반복 | 확대 버튼으로 배율 바꾸고 게이트 1을 통째로 재실행(총 54회 클릭) | 자동 |
| 3. 빈 공간 클릭 오선택 0 | 각 페이지에서 어떤 마크의 tier1·tier2에도 안 들어가는 지점을 계산해 클릭 → 선택 없음 확인 | 자동 |
| 4. 후보 목록 | **조선내화 반기엔 겹침이 없다** → 삼성 p119(A1×A2 동일 box)로 실데이터 확인. 후보 2건이 뜨고, 고르면 그 마크가 선택되는지 | 자동(다른 축) |
| 5. 링이 anchor_bbox 위치에 | 링 div의 `getBoundingClientRect()`와 §1 순변환 결과를 수치 대조(±0.5px) — **위치는 자동으로 잰다.** 다만 “눈으로 봐서 숫자를 제대로 감싸는가”는 스크린샷이 안 되는 환경이라 마지막에 체크리스트로 넘긴다 | 자동(수치) + 수동(육안) |
| 6. ★글리프 클릭 | §0-4가 드러낸 문제의 회귀 방지 — 각 마크의 **글리프 중심**을 클릭해도 그 마크가 선택되는지 18건 전수 | 자동 |

게이트 6은 스펙에 없지만 §0-4 발견 때문에 추가한다. 이게 없으면 “보이는 마크를
클릭하면 빗나간다”는 결함이 게이트를 통과해버린다.
