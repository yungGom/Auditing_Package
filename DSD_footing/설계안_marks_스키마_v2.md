## 1. 핵심 결정 A — `marks[]`를 분리할 것인가 ★가장 큰 결정

rev.2는 `mark`를 "검토 항목 1건"으로 정의하고 `type`을 **필수·2값**(`diff`|`unverified`)으로
못박았다. 그런데 현재 `marks[]` 307건 중 299건은 그 어느 쪽도 아니다(체크·사선·원·태그).
299건에 `type`을 억지로 채우면 필수 필드가 의미 없는 값으로 오염되고, 화면의 필터·
카운터·자동이동이 전부 그 위에서 돈다.

### 안 1 — 두 배열로 분리 `[되돌리기 어려움]`
```
marks[]        검토 항목만 (cross·question)          8건 — rev.2 스키마 전량 적용
annotations[]  그리기 전용 (tick·slash·circle·…)   299건 — 현행 필드 그대로
```
- 렌더러는 `marks + annotations + page_notes`를 `seq`로 병합해 재생(지금 `marks +
  page_notes`를 병합하는 것과 **같은 패턴**, 코드 추가 최소).
- 화면은 `marks[]`만 읽으면 되고, 목록·카운터가 정의대로 동작한다.
- 되돌리기 어려운 이유: 배열 구조가 바뀌므로 v1 marks.json을 읽던 코드가 전부 깨진다.
  다만 v1을 읽는 코드는 현재 `render.py` 하나뿐이다.
- **오작동 시 증상**: 병합 순서가 틀리면 오버레이 바이트가 어긋난다 → `render_gate.py`가
  즉시 잡는다(조용히 틀리지 않는다).

### 안 2 — 한 배열 유지, `type`에 3번째 값 `[되돌리기 쉬움]`
```
type: "diff" | "unverified" | "annotation"
```
- 구조 변화 없음. R-1 위험 최소.
- 대신 rev.2 명세를 우리가 고친 셈이 되고, 화면 코드가 매번 `type!="annotation"`으로
  걸러야 한다. 필터를 한 군데라도 빠뜨리면 목록에 체크 130건이 섞여 나온다.
- **오작동 시 증상**: 카운터가 조용히 부풀려진다(307 vs 8). 화면에서만 드러나고
  게이트는 못 잡는다.

### 권장 — **안 1(분리)**
근거: ① rev.2의 `type` 필수 정의를 우리가 굽히지 않아도 된다 ② 조용히 틀리는 방향
(안 2의 카운터 오염)보다 게이트가 잡아주는 방향(안 1의 병합 순서)이 안전하다 —
"미매칭 ≠ 0"과 같은 논리다 ③ 8:299라는 비율이 두 개념이 원래 다른 것임을 보여준다.

## 2. 핵심 결정 B — 좌표 규약 (R-1 직결)

rev.2는 `bbox: [x, y, w, h] pdf pt`를 요구한다. 현재는
`box: {x0, top, x1, bottom}`(pdfplumber 좌상단 원점)이다.

CLAUDE.md 설계결정 11번에 **"좌표를 반올림하지 않는다"**가 R-1 함정으로 박혀 있다.
`[x,y,w,h]`로 바꾸면 `w = x1-x0` 뺄셈이 들어가고, 렌더러가 다시 `x1 = x+w`로 복원할 때
부동소수 오차가 생길 수 있다 — 바이트가 어긋날 위험이 실재한다.

### 안 1 — `box` 원본 유지 + `bbox` 병기 `[되돌리기 쉬움]` ★권장
- `box`(pdfplumber 원본, 렌더러 전용)는 **손대지 않는다** → R-1 위험 0.
- `bbox`(rev.2 형식, 화면 전용)를 파생값으로 **추가**한다.
- 중복 저장이지만 파일이 커지는 것 외 손해가 없고, 렌더러 경로가 물리적으로 불변이다.

### 안 2 — `bbox`로 교체하고 렌더러가 복원 `[되돌리기 어려움]`
- 파일은 깔끔하지만 R-1을 정면으로 건드린다. 실패 시 4축 골든을 다시 세워야 한다.

**권장 안 1.** "중복이 못생겼다"보다 "골든이 깨진다"가 훨씬 비싸다.

> `anchor_bbox`(링 그릴 영역)는 A·B·L2 계열에서 **`bbox`와 같은 값**이다(마크가 이미
> 금액 셀에 찍힌다). 별도 조달 없이 같은 값을 넣는다. C 레퍼 `circle`만 주석번호 영역이
> 따로지만, 그건 annotations 쪽이라 이번 범위 밖이다.

## 3. 핵심 결정 C — `status` 값 변경

| 현재 | rev.2 | 비고 |
|---|---|---|
| `active` | `pending` | 이름만 다름 |
| – | `approved` | **신규** — 회계사가 "이상없음" 누른 상태 |
| `removed` | `removed` | 동일 |

`render.py`가 `status == "active"`인 마크만 그린다. 값을 바꾸면 **렌더러를 같이 고쳐야
하고, 안 고치면 지면이 통째로 비어버린다.**

- `approved`도 지면에는 계속 그려져야 한다(회계사가 승인했다고 마크가 사라지면 조서가
  아니다). → 렌더 조건은 `status != "removed"`로 바꾼다.
- 이건 렌더 조건 변경이지만 **현재 데이터에서는 결과가 동일하다**(지금 모든 마크가
  `active`뿐이라 `!= "removed"`와 `== "active"`가 같은 집합). → R-1 통과 예상.
- ⚠ 이 예상이 틀리면(=`removed` 마크가 이미 있으면) 즉시 중단 대상이다. 착수 시 4축
  전부에서 `removed` 존재 여부를 먼저 센다.

## 4. `operand_ids` — 마크로는 못 만든다 ★실측으로 확인된 문제

rev.2에서 등급을 올린 항목이다("11개 중 어느 항목이 틀렸나"). 그런데:

> 조선내화 p6 표1, `자산 총계`(A1) 마크가 있는 행: **3, 4, 8, 18, 21, 24, 34, 38**
> — 전부 합계·소계 행이다. 합계에 들어간 **성분 행에는 마크가 없다.**

`check_table`은 합계행에서만 결과를 내므로, 성분 셀은 마크가 아니다. 따라서
`operand_ids: string[]`(마크 id 배열)은 **가리킬 대상이 존재하지 않는다.**

### 안 1 — 성분 셀마다 마크를 만든다 `[되돌리기 어려움]` ✗기각
마크가 수천 건으로 불어나고, **새 마크는 곧 새 드로잉이라 R-1이 확실히 깨진다.**
지면도 체크 표시로 뒤덮인다. 기각.

### 안 2 — `operands[]`를 좌표 배열로 둔다 `[되돌리기 쉬움]` ★권장
```jsonc
"operands": [
  { "label": "현금및현금성자산", "value": "56,333,675", "bbox": [x,y,w,h] },
  …11개
]
```
- 마크를 만들지 않으므로 **드로잉이 전혀 바뀌지 않는다 → R-1 무풍.**
- 화면 요구("클릭 시 지면에서 함께 하이라이트")는 좌표만 있으면 충족된다. 하이라이트는
  pdf.js 오버레이지 틱마크가 아니다.
- `operand_ids`라는 이름은 유지하되 값이 마크 id가 아니게 되므로, **이름을 `operands`로
  바꾸는 것을 제안**한다(이름이 내용과 다르면 다음 사람이 마크 id로 오해한다).

`check_table`이 합산에 쓴 `body` 행 목록을 결과에 실어 보내면 된다 — 판정 로직은
건드리지 않고 이미 계산된 것을 버리지 않고 넘기기만 한다.

## 5. L2 편입 — 확정된 규칙

### 5-1. 그룹핑 (승인 ①②③ 반영)
```
1. (canonical_label, period_key)로 그룹 생성        → 11행 = 10그룹
2. 그룹 안에서 기준(A) 1개 선정:
     1순위  본표(BS/IS/CI/SCE/CF)가 있으면 본표
     2순위  동급이면 (page, bbox.top) 오름차순
3. 기준 = 마크 1건, 나머지 전원 = counterparts[]
```
실측 검증: 10그룹 전부 유일한 기준이 정해진다. 3중 표(지분법손익: IS·주석6·주석17)도
마크 1건 + counterparts 2건으로 떨어진다.

### 5-2. ★미해결 — L2 마크를 **양쪽에 찍는가, 기준 쪽에만 찍는가**
rev.2가 `counterparts[].mark_id`를 "상대편 마크. 클릭 시 선택 이동"으로 정의했다.
그러려면 상대편도 마크여야 한다. 그런데 승인된 규칙은 "11행 → 마크 10건"이다.
**두 요구가 충돌한다.** 세 안:

- **안 1 — 기준 쪽에만 마크, `mark_id`는 null** `[되돌리기 쉬움]`
  마크 10건 확정. 상대편으로는 `counterparts[].page`로 면 이동만 한다.
  손실: 주석 지면을 보고 있을 때 그 자리에 아무 표시가 없다. 회계사가 주석 쪽에서
  먼저 발견할 방법이 없다.
- **안 2 — 양쪽에 마크, 상대편은 `mirror` 표식** `[되돌리기 어려움]`
  마크 10 + 미러 11 = 21건이지만 카운터는 `mirror=false`만 센다(=10).
  `mark_id` 양방향 연결이 살아나고 주석 지면에도 ✗가 보인다.
  손실: **미러 마크는 새 드로잉이므로 R-1이 깨진다**(오버레이에 ✗가 추가됨).
  → 골든 갱신이 필요하고, "그려지는 마크가 같아야 한다"는 이번 게이트 조건과 정면 충돌.
- **안 3 — 이번엔 안 1, UI 셸에서 재검토** `[되돌리기 쉬움]` ★권장
  지금은 화면이 없어 미러의 가치를 실측할 수 없다. R-1을 지키는 쪽으로 두고,
  화면이 붙은 뒤 "주석 쪽에 표시가 없어 불편한가"를 실물로 판단한다.

**권장 안 3.** 근거: 이번 라운드의 게이트 조건이 "스키마만 바뀌고 그려지는 마크는
같아야 한다"이고, 안 2는 그 조건을 만족할 수 없다. 판단 근거가 없는 상태에서
되돌리기 어려운 쪽으로 가지 않는다.

### 5-3. L2 마크의 `type`
L2 CONFIRMED는 전부 `type="diff"`, `l2_class="confirmed"`.
UNDECLARED는 `type="unverified"` + `l2_class="undeclared"`로 둔다(값이 다르다는 건
확인됐지만 "같아야 하는지"가 판단된 적 없으므로 "차이"로 단정할 수 없다).

### 5-4. `counterparts[].tag` — ★명세 공백
rev.2 태그는 `"BS"|"PL"|"CE"|"CF"` **4종**인데 본표는 **5종**(BS/IS/CI/CF/SCE)이다.
매핑: BS→`BS`, IS→`PL`, SCE→`CE`, CF→`CF`, **CI→?**

정답셋 8번(전반기 FVOCI평가손익)이 **SCE vs CI**라 CI가 실제로 상대편에 등장한다.
세 갈래: ⓐ `PL`에 합침(손익계산서·포괄손익계산서를 한 묶음으로) ⓑ `CI` 태그 신설
ⓒ `OCI` 태그 신설. **화면 디자인 쪽 결정이라 판단을 요청한다.**

## 7. 못 채우거나 새로 만들어야 하는 것

### 7-1. 미검증 사유 — **지금 버려지고 있다**
`verdict="SKIP"`만 남고 **왜** 미검증인지는 저장되지 않는다. 실제 사유는
`check_table` 안에 여러 갈래로 존재한다(감사시간·인원 표 / 재작성표 / 복합통화 /
민감도 / 비율 행 / 이중분해 / 분할 미완결 / 성분 부족). rev.2의 `delta`·`formula`가
요구하는 "완성된 한국어 문장"은 이 사유 없이 못 쓴다.

→ `check_table`이 `n=0`으로 떨어뜨릴 때 **사유 코드를 함께 실어 보낸다.** 판정
결과(`n`)는 건드리지 않고 라벨만 붙이는 것이라 판정·렌더 불변. 사유 코드 → 한국어
문장 매핑은 고정 테이블로 둔다.

⚠ 사유 코드가 안 붙는 경로가 하나라도 남으면 `"미검증"`이라는 빈 문장이 화면에 뜬다 →
승인 ⑤의 원칙(조용히 빈 문자열 금지)을 따라 **`UNRESOLVED_REASON`으로 표면화**한다.

### 7-2. `sections[]` / `section_id` — 목차가 아예 없다
현재 목차 구조를 만드는 코드가 없다. 조달 가능한 재료는 있다:
- 주석: `notes.py`의 `NOTE_HEAD`가 이미 번호·제목·페이지를 뽑는다 → `depth=1`
- 본표: `statements.stmt_type()`이 본표 페이지를 판정한다 → `depth=0`
- `mark.section_id`는 마크의 페이지·표 위치를 구간에 넣어 결정(L2의 주석 귀속 로직과
  같은 방식 — 헤더 좌표 기준, `l2_extract._locate_headings` 재사용).

신규지만 재료가 전부 있어 위험은 낮다. 다만 **제목 텍스트 품질은 4축에서 재야 한다**
(§7-3과 같은 성격).

### 7-3. `table_label` 자동 추출 (승인 ⑤)
표 bbox 위쪽 최근접 텍스트 줄에서 뽑는다(`(1) 순확정급여부채의 산정내역은 다음과
같습니다` → `주석9 (1) 순확정급여부채`). `refmap.unit_texts`가 이미 "표 위쪽 최근접
(단위:) 표기"를 찾는 것과 **같은 탐색 패턴**이라 방식은 검증돼 있다.

- 4축에서 추출률·오탐률을 측정해 보고한다.
- 추출 실패는 **빈 문자열 금지 → `table_label: null` + `UNRESOLVED_LABEL` 목록에 등재**
  (승인 ⑤ 조건).
- 품질이 낮으면 `labels/{회사}.json`의 `table_aliases`(현재 0건)로 보정 — 그때
  등록 부담을 재보고한다.

### 7-4. `paper_no` — **조달원이 없다**
`"주6-14"`는 감사조서 번호다. PDF 안에 없고, 도구가 알 방법이 없다. 회계 법인·팀별
채번 규칙이라 추정도 불가하다.

세 갈래: ⓐ `null` 고정, 화면에서 빈칸(이번 라운드) ⓑ `labels/{회사}.json`류에 수동
등재 ⓒ 향후 AuditLink(조서 관리)와 연동. **판단 요청** — 권장은 ⓐ(화면이 붙기 전에
채번 규칙을 정할 근거가 없다).

## 8. 착수 순서 (승인 시) — 게이트 조건 준수

```
0. 사전 확인: 4축 marks.json에 status="removed"가 하나라도 있는지 계수 (§3 전제 검증)
1. 스키마 v2 구현 (판정 로직 무수정 — 필드 추가·재배치만)
2. 4축 marks.json 재생성 → run_gates.py 24지표 전량 일치 확인
3. render_gate.py (골든 갱신 전) 실행
     · 통과      → 드로잉 불변 입증. 4로 진행
     · 불일치    → ★즉시 중단·보고 (스키마 변경이 그림을 바꿨다는 뜻)
4. render_gate.py --update 로 골든 갱신 (파일 구조 변경분 반영)
5. 갱신 전후 오버레이 PDF 시각 대조 (페이지 표본 추출)
6. L2 편입 → 조선내화 반기 10마크 생성 확인, 정답셋 11건 추적성 유지 확인
7. 4축 재실행 + 문서 갱신
```

3번이 이번 작업의 진짜 관문이다. **`--update`를 3번보다 먼저 돌리지 않는다** — 먼저
갱신해버리면 "그림이 바뀌었는지"를 영영 못 본다(CLAUDE.md의 스탬프 함정과 같은 실수).

그대로 노출된다(빈 문자열 금지).

### 11-4. 남은 확인 요청 2건

1. **`SCE` vs `CE` 두 이름 공존** — `counterparts[].tag`는 승인대로 `CE`를 쓰지만,

2. **주석 counterpart의 `tag`** — rev.2 열거가 본표 5종뿐이라 주석에 쓸 값이 없다.

### 11-5. `table_label` 자동추출 품질 (승인 ⑤ — 보고 항목)

추출 규칙: 표 위쪽 `CAPTION_REACH`(140pt) 안에서 ① 소제목 표지(`가.`/`(1)`/`1.`)로
시작하는 줄 → ② `…다음과 같습니다`로 끝나는 줄 → ③ 없으면 **None**(추측 금지).
'가장 가까운 줄'을 그대로 쓰면 줄바꿈된 문장의 꼬리("…고 있습니다")를 집는 것이
실측으로 확인돼 이 우선순위를 넣었다. 페이지 최상단에서 시작하는 첫 표는 앞
