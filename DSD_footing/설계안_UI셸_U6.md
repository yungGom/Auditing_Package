# UI 셸 U-6 설계안 — 판단 저장 · 검토 결과 요약 · 최종 출력

승인 대기. **구현 착수 금지.** 범위는 `ui/` 아래 + 신규 파일, 판정 파이프라인 무수정.

## 0. 선행 조사 결과 (실측)

**(가) `render.py`는 그대로 쓸 수 있다.** CLI가 이미 갖춰져 있다:
```
python render.py <pdf> --marks <marks.json> [--pages 12,13] [--out] [--quiet]
```
`render.py:120`이 `status != "removed"`인 것만 그린다(결정 12). **최종 출력은
편집된 marks.json을 넘기는 것만으로 끝난다 — 렌더러에 새 코드가 필요 없다.**
부분 렌더(`--pages`)도 이미 있고, 출력 경로를 읽기·쓰기 양쪽에 쓰는 함정도
이미 `BytesIO` 전량 버퍼링으로 해결되어 있다(결정 11).

**(나) marks.json은 514KB, 그중 검토 항목은 18건뿐이다** (조선내화 반기연결).
`annotations` 299건 + 좌표가 대부분을 차지한다. 판단이 바뀌는 것은 `marks[]` 18건의
`status`·`comment`·`reviewed_*` 네 필드뿐이다.

**(다) 기존 예외색인 엑셀은 8개 시트다**: `A_예외색인` · `B_본표간연계` ·
`C_본표주석레퍼` · `F_일관성` · `D_줄글표기` · `표파싱실패` · `C7_주석참조` · `요약`.
`요약` 시트에는 **도구 실행 결과만** 있다(A/B 건수, 파라미터, 도구 버전, 실행 일시).
**회계사 판단은 한 줄도 없다** — 있을 수 없다, 분석 시점에는 판단이 없으니까.

**(라) UI 브리지는 읽기 전용이다.** `ui/api.py`가 `get_pdf`/`get_marks`/
`get_glyph_offsets` 셋만 노출한다. 쓰기 메서드가 없다.

## 1. 판단 결과 저장 — **별도 파일**(`<원본>_판단.json`)

### 결정과 근거

원본 `marks.json`을 덮어쓰지 않는다. 판단만 담은 작은 파일을 따로 낸다.

**덮어쓰기를 배제한 이유 — 결과로 설명한다:**
- `foot.py`를 다시 돌리면 `marks.json`이 통째로 재생성된다. **회계사가 반나절 검토한
  판단이 재분석 한 번에 전부 사라진다.** 실무에서 재분석은 흔하다(허용오차를 바꿔
  다시 돌리는 등). 이 사고는 되돌릴 방법이 없다.
- 514KB 파일 전체를 판단 한 번마다 다시 쓰는 것도 위험하다 — 쓰는 도중 앱이 죽으면
  분석 결과까지 깨진다.

**분리의 대가**: 두 파일을 같이 관리해야 한다. 이 위험은 **`source.sha256` 대조**로
막는다. `marks.json`은 이미 원본 PDF의 sha256을 갖고 있다. 판단 파일에도 같은 값을
적고, 로드 시 다르면 **판단을 적용하지 않고 경고**한다("다른 PDF의 판단 파일입니다").

### 파일 형식

```json
{
  "schema": "dsd-footing-review/1",
  "source_pdf": "[조선내화]반기연결검토보고서(2026.08.13).pdf",
  "source_sha256": "…",
  "marks_run": "2026-08-29 14:12",
  "reviewer": "moonyong",
  "judgments": {
    "cross:A5:p8:t1:r12:c2": {
      "status": "approved", "comment": "지분법 반영 후 일치 확인",
      "reviewed_at": "2026-08-29 15:03", "reviewed_by": "moonyong"
    }
  }
}
```

마크 id를 키로 쓴다 — 같은 실행의 marks.json 안에서만 쓰이므로 C안 키(§2, 재실행 간
안정성이 필요)와 달리 id로 충분하다. 재분석하면 `marks_run`이 달라지고, id가 바뀐
항목은 **적용되지 않고 목록으로 보고**한다(조용히 버리지 않는다).

### 저장 시점 — **판단 즉시 저장**

"앱이 죽으면 판단이 날아가는 것이 실무에서 가장 나쁘다"는 지적 그대로다. 판단 버튼을
누를 때마다 파일을 쓴다. 판단 파일은 마크 18건 기준 수 KB라 즉시 쓰기 비용이 없다
(514KB를 매번 쓰는 것과 다른 이유이기도 하다).

⚠ **원자적 쓰기**: 임시 파일에 쓰고 `os.replace`로 교체한다. 쓰는 도중 죽어도 이전
판단이 남는다. 같은 파일에 직접 쓰면 반쯤 쓰인 JSON이 남아 다음 실행에서 전부 잃는다.

### 브리지 추가

`ui/api.py`에 `save_judgment(mark_id, payload)` 하나. **쓰기 대상은 판단 파일뿐이고
`marks.json`·PDF에는 절대 쓰지 않는다** — 분석 산출물은 UI가 손대지 않는다는 U-1
이래의 경계를 유지한다.

## 2. 검토자 이름 — 첫 실행 시 1회 입력

승인하신 대로 로그인 체계를 만들지 않는다. `ui/config.json`에 이름 하나만 저장하고,
없으면 첫 실행 시 한 번 묻는다. **`.gitignore` 대상**(사람 이름이 저장소에 들어가면
안 된다) — 현재 `.gitignore`에 `ui/config.json`이 없으므로 **추가한다.**

## 3. 검토 결과 요약 — **PDF 마지막 장 + 판단 파일. 엑셀은 안 만든다**

### 형식 결정과 근거

| 안 | 판단 |
|---|---|
| **PDF 마지막 장에 요약 페이지 추가** | **채택.** 조서에 들어가는 것은 틱마크 PDF다(결정 3: 주 산출물은 PDF). 요약이 같은 파일 안에 있으면 조서 한 건으로 끝난다 |
| 별도 xlsx | **기각.** 기존 예외색인과 **중복**된다. 지적하신 그대로다 |
| 기존 예외색인에 시트 추가 | **기각.** 예외색인은 `foot.py`(분석)가 만드는 파일이고 판단은 그 뒤에 생긴다. 판단이 반영되려면 분석을 다시 돌려야 하는 모순이 생긴다 |

**기존 예외색인과의 관계**: 역할이 다르다. 예외색인은 **분석 시점의 근거 자료**(어떤
표의 어떤 행이 왜 걸렸는가), 요약 페이지는 **검토 종료 시점의 결과**(무엇을 보고
어떻게 판단했는가). 조서에는 둘 다 들어가되 중복이 아니다 — 지금도 예외색인에는
회계사 판단이 한 줄도 없다(§0-다).

### 요약 페이지 내용

```
DSD 풋팅 검토 결과 요약
문서: [조선내화]반기연결검토보고서(2026.08.13).pdf
검토자: moonyong          검토 완료일: 2026-08-29
도구 버전: db9e69d        분석 일시: 2026-08-29 14:12

  도구 지적          18건
    이상없음 / 확인함    12건
    차이 아님 / 해당없음   4건   ← 지면에서 제외됨
    미검토              2건   ★ 있으면 눈에 띄게

  판단 내역
    p8  법인세비용차감전순이익  차이 아님  "지분법 반영 후 일치 확인"
    p6  순확정급여자산       이상없음   (메모 없음)
    …

  이 도구는 표시된 수치 사이의 정합성만 검증합니다.
  원장·조서 대사는 별도 절차입니다. 자동 판정은 추천이며 확정은 회계사입니다.
```

⚠ **미검토가 남아 있으면 요약 상단에 경고를 넣는다.** 검토가 끝나지 않은 조서가
끝난 것처럼 보이면 안 된다.

### 렌더 방식

**`render.py`를 건드리지 않는다.** 신규 `summary.py`가 reportlab으로 요약 1장을
만들고, `pypdf`로 틱마크 PDF 뒤에 붙인다. 렌더러는 여전히 하나다(결정 11) — 요약
페이지는 원본 지면 위에 그리는 마크가 아니라 **새로 만드는 별지**라 성격이 다르다.

⚠ **R-1 영향**: 요약 페이지는 기존 페이지의 바이트를 바꾸지 않으므로 `render_gate.py`
(페이지별 오버레이 해시)는 영향받지 않는다. **다만 최종 출력 파일명을 분리해야 한다** —
`<원본>_틱마크.pdf`(게이트 대상, 불변)와 `<원본>_검토완료.pdf`(요약 포함)를 나눈다.
같은 파일에 덧붙이면 게이트가 페이지 수 변화를 불일치로 잡는다.

## 4. 최종 PDF 출력 — `render.py` 재사용

```
편집된 판단 → marks.json 사본에 status 반영(메모리) → render.render_all()
            → <원본>_검토완료.pdf → summary.py가 요약 1장 append
```

원본 `marks.json`은 읽기만 한다. `status`를 반영한 **사본**을 메모리에서 만들어
넘긴다. 부분 렌더는 쓰지 않는다 — 최종 출력은 전량 렌더가 맞다(판단이 여러 지면에
걸쳐 있고, 부분 렌더는 편집 후 미리보기용이다).

## 5. 마크 종류별 출력 토글 — **넣지 않는다**

지적하신 대로 먼저 실무 필요성을 판단했다.

**결론: 필요 없다.** 근거:
- 종이 조서는 모든 마크를 다 찍는다. ✓를 빼면 "이 항목은 검증하지 않았다"와
  "검증했고 맞았다"가 지면에서 구분되지 않는다 — 이 도구의 존재 이유를 지우는 방향이다.
- 결정 5가 "마크 정의(고정)"로 ✓=산술 일치를 못박았다. 빼는 선택지를 두면 그 정의가
  흔들린다.
- 실물 규모도 문제가 아니다. 조선내화 반기연결 317개 마크가 34페이지에 흩어진다.

**대신 남길 것**: 요약 페이지에 마크 종류별 건수를 적어 "✓ N개를 쳤다"를 숫자로
남긴다. 지면에서 세지 않아도 된다.

## 6. C안과의 접점 — 자동 반영 없음, 복사 편의만

승인하신 방향 그대로. UI에서 "차이 아님"으로 판정한 항목을 **`ERRORS.json` 형식
문자열로 보여주기만** 한다(클립보드 복사 버튼). 회계사가 보고 직접 옮긴다.

```
"key": "p8|A5|-3405862|1927412",
"account": "법인세비용차감전순이익",
"reason": "지분법 반영 후 일치 확인",     ← UI 메모가 들어감
"task": ""                              ← 회계사가 채운다(비면 게이트가 거부)
```

`task`를 비워 두는 것이 의도적이다 — 그대로 붙여넣으면 C안 로더가 "task 없음"으로
거부한다. **복사만으로는 선언이 성립하지 않는다.**

⚠ UI는 `ERRORS.json`을 **읽지도 쓰지도 않는다.** 형식 문자열만 만든다.

## 8. 게이트 계획

| # | 확인 |
|---|---|
| 1 | 판단 → 판단 파일 즉시 기록 (CDP로 판단 후 파일 내용 대조) |
| 2 | 앱 재시작 후 판단이 복원되는가 (실제 프로세스 재기동) |
| 3 | 원자적 쓰기 — 쓰기 도중 중단 시 이전 판단 보존 (임시 파일 잔존 확인) |
| 4 | 다른 PDF의 판단 파일 → 적용 안 하고 경고 (sha256 불일치 합성) |
| 5 | id가 바뀐 항목 → 조용히 버리지 않고 목록 보고 (합성) |
| 6 | `status=removed` 항목이 최종 PDF에서 빠지는가 (페이지 마크 수 대조) |
| 7 | 요약 페이지 숫자가 판단 파일과 일치하는가 (전수) |
| 8 | 미검토가 남으면 요약에 경고가 뜨는가 |
| 9 | **5축 게이트 전부 무영향** — `<원본>_틱마크.pdf`가 불변인지 |

## 9. 승인 요청

1. **§1 판단을 별도 파일로 분리** (덮어쓰기 배제) + sha256 대조 + 즉시 원자적 쓰기
2. **§3 요약을 PDF 마지막 장에 붙이고 별도 엑셀은 안 만드는 것**
3. **§3 최종 출력 파일명 분리**(`_틱마크.pdf` 유지 / `_검토완료.pdf` 신규) — R-1 보호
4. **§5 마크 종류별 출력 토글을 넣지 않는 것**
5. 설계안 전체
