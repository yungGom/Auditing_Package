# 설계안 — UI 셸 U-1 (PyWebView + pdf.js 최소 표시) · 승인 대기, 구현 착수 전

> 상태: **설계안만. 승인 전 구현 금지.**
> 범위: U-1(오버레이 PDF 표시)만. marks.json 읽기·좌측 목록·클릭 판정은 다음 단계.
> 기존 파일(`final.py`/`render.py`/`marks.py`/`core.py` 등 판정·렌더 경로) **무수정** —
> 신규 파일만 추가한다.

## 0. 확인한 전제 (구현 전 조사)

- 오버레이 PDF(`<원본>_틱마크.pdf`)의 한글은 **원본 DART PDF의 임베디드 폰트**에서
  온다. `render.py`가 reportlab으로 그리는 텍스트는 전부 ASCII(숫자·`+`/`-`·`/BS`·
  `FN6` 등)라 오버레이 자체는 한글 폰트가 필요 없다 — 폰트 문제가 있다면 원본 PDF
  임베딩 쪽이지 우리 드로잉 쪽이 아니다. (근거: `render.py`의 `setFont` 호출 6곳
  전부 `Helvetica`/`Helvetica-Bold`, 한글 문자열 없음)
- 조선내화 반기 오버레이 PDF 실측 670KB — 통째로 메모리에 올려도 부담 없는 크기.
- Python 3.14. `pywebview`가 아직 이 버전 휠을 내는지는 설치 시 확인이 필요하다
  (설계를 막는 문제는 아니고, 구현 착수 시 첫 번째로 부딪힐 리스크로 기록해 둔다).
- `intake_check.py`는 `core.py`/`statements.py`/`tieout.py`의 함수 시그니처만
  본다 — UI 신규 파일은 이 가드와 무관하다.

## 1. 핵심 결정 — PDF를 화면에 넣는 방법 ★가장 큰 결정

게이트 5("네트워크 요청이 0건")를 문자 그대로 만족시키려면 **로컬 서버조차 두지
않는 것**이 유리하다. 두 안을 비교한다.

### 안 1 — PyWebView JS 브리지로 바이트 직접 전달 `[되돌리기 쉬움]` ★권장
```
python 진입점(app.py)
  → PDF 파일을 통째로 읽어 base64로 인코딩
  → pywebview의 js_api(Api 클래스)로 노출: Api.get_pdf()
JS 쪽
  → window.pywebview.api.get_pdf() 호출 (HTTP 아님 — 웹뷰 엔진의 네이티브
    브리지, Windows에서는 WebView2의 postMessage 계열)
  → pdfjsLib.getDocument({data: bytes}) 로 바로 파싱 (URL fetch 없음)
```
- DevTools Network 탭에 **아무 요청도 안 뜬다** — 브리지 호출은 네트워크가 아니다.
- 여는 파일이 "PyWebView 실행 시 넘겨준 그 경로 하나"로 고정된다 — JS 쪽에
  임의 경로를 읽는 API를 열어주지 않아도 되므로 공격 표면이 작다.
- 단점: pdf.js의 **공식 뷰어(`viewer.html`/`viewer.js`)를 그대로 못 쓴다** — 그건
  URL 기반 로딩을 전제로 만들어져 있다. 대신 pdf.js **코어 라이브러리**만 갖다
  쓰고 캔버스 렌더링·페이지 넘김·확대는 우리가 짜야 한다. (다만 U-1 범위 자체가
  "페이지 넘기기·확대/축소·페이지 점프" 3개뿐이라 공식 뷰어의 툴바·썸네일·검색·
  주석편집 등 대부분은 애초에 안 써도 된다 — 되레 범위에 맞는 절제.)

### 안 2 — 로컬 루프백 서버(127.0.0.1) + 공식 pdf.js 뷰어 `[되돌리기 쉬움]`
```
python이 임의 포트로 http.server(또는 최소 asgi) 기동, 127.0.0.1 바인딩
  → /viewer.html?file=... 로 PyWebView 창이 접속
  → 공식 viewer.js가 fetch()로 PDF를 Range 요청하며 로드
```
- pdf.js 공식 뷰어를 거의 그대로 쓸 수 있어 페이지네이션·확대 UI가 이미 완성돼
  있다 — 개발량이 적다.
- 단점: **DevTools Network 탭에 localhost 요청이 찍힌다.** 외부로 나가는 건
  전혀 없지만(루프백 바인딩, 방화벽 인바운드 없음) "0건"이라는 문구를 문자 그대로
  못 지킨다 — 게이트 문구와 실제 안전성이 어긋나는 지점.

### 권장 — **안 1**
근거: 게이트 문구("네트워크 요청 0건")를 우회 해석하지 않고 그대로 만족시킬 수
있고, U-1 범위가 애초에 작아 공식 뷰어의 이점(완성된 UI)이 크지 않다. 서버를
안 띄우면 포트 충돌·방화벽 팝업·백그라운드 프로세스 정리 같은 부수 문제도 같이
없어진다.

**다만 확인 요청**: 게이트 5의 "0건"이 정말 안 1 수준(브리지 호출까지 무)을
요구하는 것인지, 안 2 수준(외부 인터넷 요청만 없으면 됨)도 허용인지 — 안 1로
진행하되, 이 해석이 맞는지 확인 부탁한다.

## 2. 최소 뷰어 구성 (안 1 채택 시)

```
ui/
  app.py              PyWebView 진입점 — python ui/app.py <오버레이_PDF.pdf>
  api.py              Api 클래스 (js_api) — get_pdf() 하나만 노출
  web/
    index.html         뷰어 페이지 (캔버스 1장 + 하단 툴바)
    viewer.js           pdf.js 코어 호출, 페이지 렌더·이동·확대 로직
    viewer.css           최소 스타일
    vendor/pdfjs/
      pdf.mjs / pdf.worker.mjs     pdf.js 코어 (뷰어 UI 없이 라이브러리만)
      cmaps/                       임베디드 CID 폰트 안전망(비상시)
      standard_fonts/              비임베디드 표준폰트 안전망(DART PDF엔 불필요할
                                    가능성이 높지만 용량이 작아 같이 넣어 둔다)
```

- 진입점 인자는 `foot.py`와 통일된 스타일로 **오버레이 PDF 경로 하나**만 받는다.
  실행 예: `python ui/app.py "samples/[조선내화]반기연결검토보고서(2026.08.13)_틱마크.pdf"`
- 화면 구성: 위에서부터 [◀ 이전][페이지 입력][/ 총 N][다음 ▶] · [− 확대 +] ·
  중앙에 현재 페이지 캔버스. 그 이상 UI 요소를 넣지 않는다(요청대로).
- 지면은 **캔버스에 pdf.js가 그린 래스터**다. HTML로 다시 그리지 않는다(요청대로,
  틱마크·글자 위치가 좌표 계산이 아니라 PDF 자체 렌더 결과이므로 좌표 오차가
  원천적으로 없다).
- 렌더 해상도는 화면 DPI(devicePixelRatio)를 반영해 캔버스 픽셀 크기를 잡는다 —
  그러지 않으면 확대 시 글자가 흐려져 게이트 2(한글 안 깨짐) 판정이 애매해진다.

## 3. pdf.js 조달 (개발 시 1회 네트워크 필요 — 승인 필요)

- 출처: Mozilla 공식 `pdfjs-dist` 릴리스(GitHub Releases 또는 npm 레지스트리).
  라이선스 Apache-2.0 — 오프라인 재배포에 문제없다.
- **개발 머신에서 1회 내려받아 저장소에 그대로 커밋**한다(런타임에는 절대
  네트워크를 타지 않음 — vendoring). `pdfplumber`/`reportlab`을 pip로 설치한 것과
  같은 성격의 "개발 시 조달, 배포본은 오프라인"이다.
- 버전은 조달 시점 최신 안정판을 쓰고, `ui/web/vendor/pdfjs/VERSION.txt`에 버전과
  다운로드 출처·SHA256을 기록해 둔다(재현성·라이선스 추적).
- **승인 필요**: 이 1회 다운로드를 지금 진행해도 되는지 확인 요청. (도구 자체
  실행에는 영향 없음 — Playwright 브라우저 바이너리와 같은 "개발 전용 조달".)

## 4. Playwright 도입 — 무엇을 테스트하는가

### 4-1. 실제 PyWebView 창을 검증 대상으로 삼는다 `[권장]`
Windows의 pywebview 기본 엔진은 WebView2(Chromium 기반)다. 개발 실행 시에만
디버그 포트를 열면(`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9222`,
개발용 환경변수로만 설정 — 배포본에는 없음) Playwright가
`chromium.connect_over_cdp("http://127.0.0.1:9222")`로 **실제로 회계사가 보는
그 창**에 붙어 스크린샷·DOM·네트워크 로그를 확인할 수 있다.

대안(표준 Chromium 탭에 같은 HTML을 단독으로 띄워 테스트)은 pywebview 브리지가
없어 `window.pywebview.api`를 스텁으로 대체해야 하고, 게이트 5(네트워크 0건)를
"진짜 배포 환경"이 아니라 대역으로만 검증하게 된다 — 신호가 약하다. 이번엔 CDP
어태치를 쓴다.

### 4-2. 의존성 분리
```
requirements.txt        (런타임 — 회계사 PC, 오프라인)
  + pywebview            신규 추가
requirements-dev.txt     (개발 전용 — Claude Code/개발자 PC만)
  playwright
```
- `requirements-dev.txt`의 패키지는 PyInstaller 빌드에 포함하지 않는다.
- **확인 필요**: `requirements.txt`는 기존 파일이라 "U-1은 신규 파일만 추가,
  기존 파일 수정 금지" 지시와 문자 그대로는 충돌한다. pywebview 의존성 등록은
  이 규칙이 보호하려는 대상(GATES/RENDER_GATE에 걸리는 판정·렌더 코드)이 아니라고
  보고 예외로 진행해도 되는지 확인 요청. (CLAUDE.md도 신규 파일 추가 시 파일
  색인에 한 줄 추가하는 걸 기본 규칙으로 두고 있어, 순수 문서·의존성 성격의
  기존 파일 변경까지 막는 취지는 아니라고 해석했다 — 맞는지 확인 바란다.)

### 4-3. 게이트 1~5 자동화 방식
| 게이트 | 확인 방법 |
|---|---|
| 1. 정상 표시 | CDP로 첫 페이지 캔버스 스크린샷 → 파일 크기·비트맵이 빈 화면(단색)이 아닌지 |
| 2. 한글 안 깨짐 | 본표 페이지(예: p6 재무상태표) 스크린샷을 사람이 눈으로 대조(자동 OCR은 설계상 금지 — CLAUDE.md 절대 규칙) |
| 3. 마크 동일 렌더 | 같은 페이지를 pypdfium2(또는 기존 결과물 뷰어)로 별도 래스터화한 것과 pdf.js 스크린샷을 픽셀 비교(허용 오차 있는 diff) — 완전 자동 비교가 불안정하면 사람 눈 대조로 폴백 |
| 4. 페이지 이동 지연 | Playwright로 "다음" 클릭 → 캔버스 갱신까지 걸린 시간 측정, 임계값(예: 300ms) 이하인지 |
| 5. 네트워크 0건 | CDP `Network.requestWillBeSent` 이벤트 리스너를 등록해 두고, 페이지 로드+조작 전체 구간에서 발생 건수가 0인지 |

게이트 3(픽셀 비교)은 오탐 여지가 있다 — 안티앨리어싱 차이 등으로 완전히 0오차는
아닐 수 있다. 이번 라운드는 **사람이 스크린샷을 보고 최종 판정**하는 것을
1차로 하고, 픽셀 diff는 참고 신호로만 쓴다(자동 판정에 근거 약한 수치를 쓰지
않는다는 프로젝트 원칙과 일치).
