> 범위: 목록 클릭이 지면을 페이지 단위로 이동시킨다. 좌표 매칭·하이라이트는 U-4,
> 역방향(지면→목록)도 U-4. `ui/` 아래만 건드린다.

## 0. 확인한 데이터
조선내화 반기 18건 전부 `table_label`이 채워져 있다(null 없음 — U-1/U-2 사이

## 1. 핵심 결정 — sidebar.js ↔ viewer.js를 어떻게 연결하는가

지금 두 모듈은 서로 모르는 사이다(U-1/U-2가 의도한 관심사 분리). U-3은 처음으로
"목록 클릭 → 지면 이동"이라는 **단방향** 연결이 필요하고, 예고하신 대로 U-4에서는
**역방향**(지면 클릭 → 목록 선택)까지 필요해진다.

### 안 1 — 직접 import `[되돌리기 쉬움]`
`sidebar.js`가 `viewer.js`에서 `export function jumpToPage(n)`를 가져다 쓴다.
간단하지만 **역방향이 필요해지는 순간 두 모듈이 서로를 import하게 된다**(순환
참조) — U-4에서 다시 뜯어고쳐야 할 게 거의 확실하다.

### 안 2 — 작은 이벤트 버스 신설 `[되돌리기 쉬움]` ★권장
```
ui/web/bus.js   on(event, fn) / emit(event, payload) 10줄짜리 pub/sub
```
- `sidebar.js`: 행 클릭 시 `emit('selectMark', markId)`
- `viewer.js`: `on('selectMark', ...)`를 구독해 페이지 렌더. 그리고 **페이지가
  바뀔 때마다**(list 클릭이든 이전/다음 버튼이든 페이지번호 직접 입력이든)
  `emit('pageChanged', n)`도 낸다
- `sidebar.js`: `on('pageChanged', ...)`를 구독해, 새 페이지가 현재 선택된
  마크의 페이지와 다르면 선택 해제 + 툴바 표 이름 비움(수동으로 페이지를
  넘겼는데 목록엔 옛 항목이 선택된 채로 남는 상황 방지)

순환 참조가 없고(둘 다 `bus.js`만 import), **U-4의 역방향 연결이 이미 뚫려
있다** — 그때 가서 구조를 다시 짤 필요가 없다. 지면 클릭 이벤트도 같은 버스에
`emit('selectMark', markId)`를 내면 끝이라, U-4는 "지면 클릭 위치를 어느 마크에
매칭할지"(진짜 어려운 부분)에만 집중할 수 있다.

**권장 안 2** — 예고하신 "U-4가 가장 위험한 단계"라는 판단과 같은 방향이다.
지금 구조를 잘 잡아두면 U-4에서 좌표 문제만 남는다.

## 2. 선택 표시 · 툴바 표 이름

- 선택 행: `.row.selected { border-left: 3px solid var(--red); background: var(--gray-100); }`
  (기존 3색 원칙 안 — 새 색 없음)
- 툴바에 `<span id="tableLabel">`을 추가한다. **표 이름은 페이지가 아니라
  선택된 마크에 종속**이다 — 한 페이지에 표가 여럿일 수 있어서다. 규칙:
  - 목록 클릭/N/J/K로 마크가 선택되면 → 그 마크의 `table_label`(없으면
    `"표 이름 미확인"`, 빈칸 금지)
  - 이전/다음 버튼·페이지 직접 입력 등 **마크 선택 없이** 페이지가 바뀌면 →
    표 이름 칸을 비운다(옛 선택의 이름이 남아있으면 오해를 부른다)

## 3. 키보드

- **J/K** — 현재 필터 탭에 **보이는** 행 안에서 선택 위/아래 1칸 이동. 경계에서
  멈춘다(순환 안 함 — 스펙에 순환이 명시된 건 N뿐이라 다르게 뒀다, 아니면 J/K도
  순환시킬지 확인 요청).
- **N** — `status==="pending" && type==="diff"` 인 마크만, `page` 오름차순으로
  순회, 마지막에서 처음으로 순환. **현재 필터 탭이 "차이"가 아니면 자동으로
  "차이" 탭으로 전환한다** — 그래야 이동한 항목이 실제로 목록에 보이고
  스크롤이 따라갈 수 있다(안 바꾸면 게이트 4 "뷰포트 안 유지"를 만족 못 시키는
  경우가 생긴다).
- 입력 포커스가 `#pageNum`(페이지 번호 입력창) 등 폼 요소에 있을 때는 J/K/N을
  무시한다 — 숫자 타이핑을 가로채면 안 된다.
- 선택 로직은 행 클릭과 키보드가 **같은 내부 함수**(`selectMark(mark)`)를 공유한다
  — 표시·스크롤·버스 emit이 한 곳에만 있어야 나중에 어긋나지 않는다.

## 4. 게이트 자동화 계획

| 게이트 | 방법 |
|---|---|
| 1. 18건 전수, 페이지 일치 | "모두" 탭에서 각 행을 실제로 클릭(표본 아님, 18회 반복) → `#pageNum` 값이 `mark.page`와 일치하는지 매번 확인 |
| 2. 선택은 항상 1개 | 클릭 후 `.row.selected` 개수가 항상 1인지 매 클릭마다 확인 |
| 3. N 순회 | `pending && diff` 14건의 `id` 목록을 미리 계산 → N을 14번 눌러 선택 순서가 그 목록과 일치, 15번째에 첫 항목으로 순환하는지 확인 |
| 4. J/K 뷰포트 유지 | 선택 행의 `getBoundingClientRect()`가 `#markList`의 `getBoundingClientRect()` 안에 들어오는지(스크롤 top/bottom 비교) — 끝까지 이동하며 확인 |
| 5. 툴바 표 이름 일치 | 18건 각각 클릭 후 `#tableLabel` 텍스트 == `mark.table_label` 대조. **UNRESOLVED 분기는 이 샘플에 없으므로**, `evaluate()`로 한 마크의 `table_label`을 메모리상에서 일시적으로 `null`로 바꿔 다시 선택시켜 `"표 이름 미확인"`이 뜨는지 별도 합성 검증(실 데이터 검증과 분리해 보고) |

깜빡임·잔상처럼 수치로 못 재는 것만 사람 몫으로 남기겠습니다 — 페이지 전환
자체가 U-1의 `renderPage()`를 그대로 재사용(로직 변경 없음)이라 새로운 시각적
위험은 적다고 보지만, 완료 후 실제로 눌러보시고 어색하면 알려주십시오.
